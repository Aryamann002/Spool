# Spool — Agent Instructions

## Project

Spool is an open-source local design agent powered by small language models. This repository directory contains its marketing/landing website: an interactive visual experience demonstrating what Spool can generate.

This is not a conventional SaaS landing page. The primary goal is to make visitors feel as if they have entered a physical creative workspace containing artifacts generated by Spool.

## Source of truth

Before modifying the project, read these files in order:

1. `AGENTS.md`
2. `DESIGN.md`
3. `PLAN.md`
4. `.agents/skills/emil-design-eng/SKILL.md`

Visual references supplied to the repository are also part of the design source of truth. The Emil design-engineering skill and Spool's specific visual direction are separate documents: the skill describes general design-engineering practice; `DESIGN.md` describes Spool.

When sources conflict, follow this precedence:

1. Explicit user instructions
2. `DESIGN.md`
3. `PLAN.md`
4. `.agents/skills/emil-design-eng/SKILL.md`
5. Existing implementation

Never silently reinterpret the design to make implementation easier. If something is ambiguous, preserve the established visual direction. If a required source or brand asset is missing, identify it rather than inventing a replacement.

The Emil design-engineering skill is maintained separately from Spool's project-specific direction and is copied into `.agents/skills/emil-design-eng/SKILL.md` for this repository. The website also includes a candidate wordmark font at `public/fonts/wobble.ttf` and visual references under `public/images/`. Verify the candidate font against the Spool concept image before using it as the exact logo typeface. Do not substitute another font or alter/move supplied references without a reason.

## Primary objective

Build an interactive Spool website with this experience:

VOID → paper/fabric canvas appears → fixed-position puzzle silhouettes reveal the actual landing-page world in place → the complete composition is briefly visible → temporary puzzle pieces disappear → ready-for-thread → (later phases) black thread draws the Spool logo → camera pulls back → visitor explores the larger world.

The loading puzzle pieces are introduction only. After loading, there must be zero puzzle pieces in the main world. Do not use puzzle pieces as permanent decoration.

## Non-negotiable design constraints

### Do not make a generic SaaS landing page

Do not introduce centered SaaS hero layouts, gradient backgrounds, glassmorphism, glowing blue/purple AI aesthetics, floating 3D blobs, generic feature cards or AI illustrations, excessive rounded containers, or conventional vertical marketing sections.

The website should feel editorial, physical, tactile, strange, intentional, and art-directed.

### The main website is a physical canvas

Treat the site as a large 2D world and the browser viewport as a camera looking at it. Visitors can drag the world to explore it. World artifacts should be independent DOM elements, not flattened into one giant background image. Artifacts may include generated website mockups, posters, photographs, UI designs, typography experiments, sketches, terminal windows, handwritten notes, color palettes, diagrams, and code fragments.

### Preserve the Spool wordmark

Use only the exact Spool wordmark/font or vector supplied by the user. Never approximate it with a generic typeface. If the actual logo asset is unavailable, report that before implementing the logo. The reveal should resemble black thread physically drawing the wordmark.

### Motion is part of the identity

Use `.agents/skills/emil-design-eng/SKILL.md` for design-engineering principles when it is available. Do not animate merely because the technology allows it; every major animation needs a purpose.

## Engineering principles

Keep the architecture understandable. Prefer React, TypeScript, CSS, SVG, Motion where appropriate, browser Pointer Events, and browser APIs. Do not add large animation/rendering libraries unless they solve a demonstrated problem. Do not introduce Three.js, WebGL, or a canvas rendering engine just because the site is interactive; begin with normal DOM elements and transforms.

### World model

The conceptual camera is:

```ts
type Camera = {
  x: number
  y: number
  scale: number
}
```

World items are conceptually:

```ts
type WorldItem = {
  id: string
  x: number
  y: number
  rotation: number
  scale: number
  type: string
}
```

The world is larger than the viewport. Dragging changes the camera; scrolling moves the camera toward predefined scene anchors. Do not turn every area into a conventional document-flow section.

### Performance and accessibility

- Prefer transform and opacity for movement and transitions; avoid unnecessary layout animation.
- Do not continuously update expensive React state on every pointer movement if direct DOM transforms or motion values are more appropriate.
- Use pointer capture for dragging and support touch/pointer interaction where practical.
- Respect `prefers-reduced-motion` with a calmer version of the experience rather than removing the entire interaction model.

### Responsiveness

Desktop is the primary art-directed experience. On smaller screens, the world may be more constrained and scroll-driven, but preserve its visual identity. Do not simply shrink every desktop element.

## Development process

Build incrementally and follow `PLAN.md` one phase at a time. Do not implement the entire website in one pass or build future-phase features early. After each phase, run the application, inspect it, compare it with design references, fix obvious discrepancies, report what changed, and stop for confirmation before beginning the next major phase. Do not proceed while a foundational interaction is visually broken.

## Do not invent

Do not invent sections, brand colors, logo treatments, interaction paradigms, visual styles, copy, or product claims unless explicitly requested or required by the existing design. If a missing decision blocks implementation, stop and ask rather than silently redesigning the product.

## Definition of done

The website is successful when the loading sequence feels deliberate; the paper/fabric canvas feels physical; all puzzle pieces disappear after loading; the intended Spool logo is drawn by black thread; the camera transition and world exploration feel natural; dragging and scrolling navigate intentionally; artifacts feel like things Spool could genuinely generate; the experience feels like an interactive creative workspace; and the implementation remains understandable to another developer.

The site should feel designed, not merely implemented.
